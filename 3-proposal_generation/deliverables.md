The build is complete, typechecks, passes 196 unit and 67 end-to-end tests, and produces a clean production bundle of 22 routes. It has never been deployed. **This is the highest-priority remaining task** — everything else on this page is worth less if it is not done.

**To deploy:**

```bash
cd 3/build
vercel link && vercel deploy --prod
```

Set in the Vercel project: `DATABASE_URL`, `ANTHROPIC_API_KEY`, `APP_SESSION_SECRET`, `SEED_*` credentials, and — importantly — **`APP_BASE_URL`**, without which client-facing links fall back to localhost (see F3 in the [security review](security-review.md)). Then `npm run migrate && npm run seed` against the production database, and verify from a browser that is not yours, signed out.

**Counts:** 196 unit + 67 end-to-end, 0 failures. Up from 139 + 56 at the start of this work.

**Features added on top of the PRD, both prompted by review:**
- **Review comments** — a reviewer can now ask "where did the 40k come from?" without rejecting the proposal. Previously the only feedback field hung off an approval *decision*.
- **OCR for scanned uploads** — a PDF with no text layer is read by Claude's vision from the PDF itself, reusing the base64 `document`-block pattern from the Week 1 invoice build. No OCR library, no native dependency.
- **A voice layer** — worked exemplars in the cached prefix (the prompt described the register but never showed it) plus a free deterministic style gate for stock vocabulary, flat sentence rhythm, tricolon overuse and repeated openers. See [accuracy-note.md](accuracy-note.md) §A-8.

## 4. Video walkthrough

⬜ **To record.** 5–8 minutes. Suggested structure, following the Guide's flow:

1. **Who and what** (30s) — an AI proposal studio for the Koya sales team.
2. **The problem** (45s) — proposals take hours and quality depends on who writes them.
3. **How it solves it** (45s) — intake → draft → revise → approve → deliver, with a human gate that is enforced rather than requested.
4. **Happy path** (2m) — intake with an upload, watch sections stream in, regenerate the pricing section with an instruction and show the others are untouched, submit, approve *as a second user*, deliver, open the client link.
5. **Failure paths** (1.5m) — pick two and show behaviour, not nodes:
   - Submit a sparse intake → gaps appear and **block approval**; waive one with a reason and show it land in the audit trail.
   - Try to approve your own proposal → refused. Try to open a client link before approval → nothing there.
   - Upload a scanned PDF → watch it get read anyway, and note the advisory gap telling you to check the figures.
   - Leave a review comment as the approver, answer it as the author, resolve it.
   - Optionally `/api/health` with a lane unconfigured → the honest `.eml` fallback rather than a false success.
6. **Artefacts** (30s) — `/system` page, correlation IDs, the n8n workflow JSON.
7. **Reflections** (45s) — the ownership-vs-role finding from the [security review](security-review.md) is the strongest thing to talk about: the UI hid the controls, so every manual test confirmed a boundary that did not exist.

## 5. Reflection sheet

See **[reflections.md](reflections.md)** — the five required answers in §A, a cross-project retrospective in §B, and a full ledger in §C.

**§B is the part worth reading.** Set side by side, the same mistake has now happened three times in three disguises:

| Week | What I validated | What I failed to validate |
|---|---|---|
| 1 — Invoice processing | Field presence and format | Whether the file was **readable at all** |
| 2 — Ops reporting | Field validity — dates, nulls, statuses | What a column **means** (a 20× error that announced nothing) |
| 3 — Proposal studio | The caller's **role** | The caller's **relationship to the record** |

Every time, the check I built was one level too shallow — and the fact that it existed is precisely what made the missing one invisible.

**§C** lists what was built, the eight defects found and fixed by reviewing my own work, the two features added on request, and — explicitly — what I chose *not* to build and why.

The five required answers:

1. **Clarifying questions** — five, led by whether an author may also approve, which is the question the whole build turns on.
2. **Biggest challenge** — authorisation was checked as a property of the *caller*, never as a relationship to the *record*. Root cause was a category error: having built authentication, roles and separation of duties well is exactly what made the missing fourth axis invisible.
3. **What I would do differently** — write the authorisation rules as one table *before* the routes, and derive both server checks and UI states from it. A cross-cutting rule that lives in twelve places is not enforced, it is merely usually present.
4. **Edge cases** — grouped by the assumption each breaks: bad input, model misbehaviour, repeated runs, acting out of turn, downstream outages.
5. **Model choice** — Opus 5 for client-facing prose, Haiku 4.5 for the gates; Sonnet 5 considered and rejected at both ends rather than in the middle. ~5x cheaper than all-Opus. The larger saving was noticing that the grounding check needs no model at all.
